## REQ-02 — Failover residency attack (THE crown risk)

Attack goal: find any path where an `allow_openrouter:false` job reaches OpenRouter on failover.

| # | Attack vector | Result | Severity |
|---|---|---|---|
| A1 | Does the ladder's `next_rung` ever include a third-party tier for a false-policy repo? | **BLOCKED.** §4.1 pre-filter drops third-party rungs when `_rung_admissible` is false; §4.2 step-4 only re-launches on an admissible rung; exhausted first-party → `WAIT_FOR_CAPACITY` sentinel, never an OpenRouter rung. And the ladder is drawn from `capabilities.json` `live_catalog && ping_ok`, currently empty → no OR rung exists at all today. | — (safe) |
| A2 | Is the pre-filter applied on EVERY rung or only the first? | **Design intent: every rung.** `next_rung(current, repo, policy, catalog)` re-takes `repo`+`policy` each call (§4.1 signature) and re-filters — not a cached admissible-list from `select_tier`. **BUT this is unverifiable (no code).** The pre-filter's per-rung application is a design assertion; the only *executable* guarantee is the runner wall A4. Flagged as the load-bearing implementation risk. | P1 (F1) |
| A3 | On unknown/missing policy, fail-closed (WAIT) or fall through (OpenRouter)? | **Fail-closed at the guard** (`residency_guard.py:82` `None`→raise). **But the router's pre-filter reads the policy via `load_merge_policy`, which RAISES `FileNotFoundError` on a missing file** (`merge_policy.py:169`). The design says the router "reads the policy to pick the ladder" but never specifies the router catches that raise and substitutes `default_policy` (openrouter-OFF). If the router lets it propagate, the job errors to NEEDS_ATTENTION (safe-ish); if a naive `except: pass` treats missing-policy as "no filter," the ladder keeps its OR rungs. Underspecified — see F3. | P1 (F3) |
| A4 | Runner guard on EVERY rung, or only launch? | **BLOCKED — guard is on every worker spawn.** `build_worker_env` (`:362`) runs on each `WorkerRunner.launch`, and failover re-launch (§4.2 step-4) goes through the same `launch`. A false-repo OR rung raises `ResidencyViolation` before any key. This is the real, in-prod second wall. | — (safe) |
| A5 | Does handoff-brief re-launch re-read policy or trust a stale cached tier? | **Design intent: fresh spec built by router each launch** (§4.2 "spawns it exactly as a fresh node"; §3.2 resume "Build a `WorkerRunSpec`"). But the checkpoint record **persists `rung: {worker, model, tier}`** (§3.1 JSON). If resume/failover reuses the *checkpoint's cached rung* instead of re-running `select_tier` with the live policy, a repo whose policy flipped false→(stale true-cached rung) could re-launch on a stale OR tier. The guard (A4) still catches it, so **no leak** — but the design should state the rung is RECOMPUTED on resume, not replayed from the checkpoint. See F2. | P1 (F2) |
| A6 | Can a 429 on the LAST subscription tier silently fall to OpenRouter instead of WAIT? | **BLOCKED.** §4.2 step-3 + §4.3: exhausted admissible first-party → `WAIT_FOR_CAPACITY`, park `WAITING_CAPACITY`, never dispatch OR. Assertion in test §10-P4b-#3. | — (safe) |
| A7 | Does enabling OpenRouter in P4-b remove an existing accidental wall? | **Yes — flag it.** Today `_PROVIDER_MODEL_KEY` (`worker_runner.py:52`) has **no `openrouter` entry**, so even past a bypassed guard, `.get("openrouter")→None`→no key placed (the P3-review P0-1 accident, still in force). P4-b's "enable OpenRouter workers" MUST add that entry, which **deletes this third accidental wall** and makes `assert_openrouter_allowed` the sole barrier for OR. The design leans on "two walls, the second in prod" but doesn't note wall-3 evaporates precisely when P4 lands. Correctness of the guard becomes newly load-bearing. | P2 (F7) |

**REQ-02 escalation verdict: NO failover path lets a false-policy job reach OpenRouter.** Two independent enforced walls (router pre-filter + runner guard `:362`), plus a third accidental one that P4-b removes. Crown risk **CONFIRMED-SAFE**, on the strength of the runner guard opened at `worker_runner.py:358-362`. The P1s (F1/F2/F3) are *implementation hazards that could weaken the FIRST wall* — none defeats the second.

## REQ-03 — Cost bounding attack

| # | Attack vector | Result | Severity |
|---|---|---|---|
| C1 | Failover spends on BOTH failed tier and retry — is failed spend counted? | **PARTIAL / underspecified.** `worker_cost` folds each worker's `actual_spend_usd` via `commit_spend` (§4.4). If failover re-launch calls `try_reserve` AGAIN for the retry (new node), the retry reserves a *fresh* `budget_usd` cap while the failed tier's spend is already committed. Net dollars are counted correctly (both `commit_spend` calls add real spend), so the **ceiling is not exceeded** — but a job that fails over K times reserves K× its cap transiently, which can **spuriously trip the ceiling CAS and defer/starve other jobs**. The design never states failover reuses the original reservation vs. re-reserving. Not a ceiling *breach*; a liveness/accounting-clarity gap. | P1 (F4) |
| C2 | Concurrent jobs racing the ceiling CAS | **BLOCKED.** `try_reserve` (`:260`) BEGIN IMMEDIATE + `WHERE spent+reserved+cap<=ceiling` serializes under SQLite's write lock; two racing ticks → exactly one `rowcount==1`. Verified atomic within the shared `_conn`. | — (safe) |
| C3 | Resumed job double-counts or fails to count pre-crash spend | **Underspecified.** On crash, `_reclaim_dead_job` (`job_store.py:672`) releases the *reservation* (`budget_settled` idempotent) but **does not `commit_spend` the pre-crash actual tokens** — a crashed worker's real spend is only captured if `worker_cost` metered it before the kill. On resume, the job re-runs the phase from the brief → **spends again**. So pre-crash partial spend can be under-counted (reservation returned, tokens already burned at the provider) → real spend can exceed the ledger's view. This is *accounting drift*, and its size is unbounded by the design (a job that crashes at 90% of a phase, N times). Feeds directly into the "within tolerance" gap C5. | P1 (F5) |
| C4 | OpenRouter ≤$2 sub-ceiling atomic under concurrency? | **NOT IMPLEMENTABLE AS DESIGNED (WRONG reuse claim).** The sub-ceiling is specified as a `DailyBudgetLedger` CAS "keyed to a `provider="openrouter"` row" (§4.4, §13), reusing the existing class. But `daily_budget` is `day TEXT PRIMARY KEY` with **no provider column** (`cost_stops.py:62`) — you cannot insert a second (day, openrouter) row. A *second `DailyBudgetLedger` instance* (separate DB/table) would be atomic **within itself**, but then the $5 nightly ceiling and the $2 OR ceiling live in **two connections with no shared transaction** → an OR job must pass BOTH CASes, and there is a TOCTOU window between them (reserve $5-ledger, then reserve OR-ledger; a crash/interleave between leaves the $5 reservation without the matching OR one, or vice-versa) unless the design specifies an ordering + compensating release. Neither the schema change nor the two-ledger protocol is specified; §1 explicitly (and wrongly) says "no migration." | **P1, borderline** (F6) |
| C5 | "Within tolerance" — what's the tolerance, can real spend exceed it? | **Tolerance is NOWHERE DEFINED.** The gate (plan §P4) and design §6/§11 both say "cost accounting matches provider spend within tolerance" but no number is given. `commit_spend` is explicitly overshoot-tolerant ("the ceiling becomes slightly softer post-hoc," `cost_stops.py:314`), and Codex has `budget_flag:false` (`capabilities.json`) so its cost is **post-hoc metered, not pre-capped** (§4.4 concedes this) — a Codex worker can overshoot its per-job cap by a full phase's tokens before the wall-clock stop fires. Combined with C3 (crash re-spend), real provider spend can drift above the ledger by an amount the design leaves unbounded. The reconciliation test (§11 `test_cost_accounting_reconciles_synthetic_night`) reconciles the *ledger against itself* (cost-log Σ vs `daily_budget.spent_today_usd`), NOT against real provider spend — so it cannot catch this drift. See F8 (test theater). | P1 (F5/F8) |

**REQ-03 escalation verdict:** the **$5 hard ceiling cannot be exceeded** by the pre-launch CAS (C2 blocked) — the pre-launch reserve is the real guard and it is atomic. But (a) the **$2 OpenRouter sub-ceiling is not implementable as a `daily_budget` row** (F6, a WRONG reuse claim), (b) **accounting can drift above real spend** via Codex post-hoc metering + crash re-spend with **no defined tolerance** (F5), and (c) the reconciliation test checks ledger-vs-ledger, not ledger-vs-provider (F8). No P0 (ceiling not breachable), but the cost gate is **weaker than it reads**.

## REQ-04 — Checkpoint-resume attack + gate-test verdicts

| # | Attack vector | Result | Severity |
|---|---|---|---|
| D1 | Can a resume re-run a side-effecting phase (re-merge / re-push / double-send)? | **Structurally guarded by design, but the state machine BLOCKS the whole resume path (D5).** §3.2 step-2: "re-launch from the last CLEARED boundary, never mid-phase," and MERGING is downstream of AWAITING_APPROVAL (a human/broker gate). A resume from a *cleared* REVIEW re-enters at REVIEW→AWAITING_APPROVAL, not MERGING, so it does **not** re-merge. Merge itself rides the broker held-action (idempotent per P1a stable action-IDs). So **no double-merge by design** — *if* resume were reachable. It is not (D5). | — (design-safe) but see D5 |
| D2 | Does resume-from-last-CLEARED-phase correctly NOT re-execute a cleared merge? | **Yes, by the write-ordering discipline** (§3.1: write checkpoint file THEN CAS transition; a crash between re-does an *idempotent* phase from the prior brief). MERGING has no checkpoint boundary after it except DONE, and DONE is terminal — a merged job is never resumed. | — (safe) |
| D3 | Corrupt / partially-written checkpoint resumed into a bad state? | **Mitigated:** §3.1 "atomic temp-file + rename"; §3.2 step-1 "if absent → treat as fresh." A torn write leaves the prior file intact (POSIX rename atomicity). **Gap:** no checksum/version field on `checkpoint.json`, and a *semantically* stale-but-well-formed checkpoint (e.g. artifacts paths pointing at a reaped worktree) is only partially handled (§3.2 step-4 re-creates the worktree) — a checkpoint whose recorded `branch`+base no longer exists in the repo is not covered. Minor. | P2 (F9) |
| D4 | Does forensic capture happen BEFORE kill reliably? | **Design says yes** (§3.3 "capture BEFORE kill," test §10-P4a-#4 asserts ordering via spy). Sound *as specified*. Real risk: the kill paths are **plural** — a cost-stop `SIGTERM`-to-process-group (`cost_stops` TIMEOUT/BUDGET), a stall detector, AND `check_integrity`'s `_reclaim_dead_job` which fires when the pgid is **already dead** (crash, OOM, `kill -9`). For the last class **there is no "before kill" — the worker is already gone**, so `capture_bundle` runs post-mortem against a dead worktree (transcript tail may be truncated, no live handle). The design's "capture before kill" holds only for *supervised* kills, not crashes — yet the gate's headline case is a *crashed* worker. Under-scoped. | P1 (F10) |
| D5 | **Crashed-worker resume vs. the reused one-way state machine** | **CONTRADICTION.** `_ALLOWED` (`job_store.py:85`) makes `NEEDS_ATTENTION` **terminal** (empty frozenset), and `check_integrity`→`_reclaim_dead_job` (`:672`) moves every dead-pgid job **directly to NEEDS_ATTENTION**. `tick` runs `check_integrity` as **step 0** (`scheduler.py:205`), so a crashed worker is parked terminal *before* any resume branch runs. The design (§5.1) says the tick "resumes a crash-detected job via `phase_checkpoint.resume`" and claims (§1 job_store row) "no new states needed for checkpoint" — but there is **no NEEDS_ATTENTION→RUNNING edge, and no WAITING_CAPACITY state in `_ALLOWED` at all.** As written, the flagship gate's "≥1 crashed worker resumes from a phase checkpoint" **cannot be implemented on the cited-reused machine** without adding a resumable state + edge the design denies needing. | **P1** (F11) |

## Findings ledger (severity-ordered)

- **F11 [P1]** Crash-resume contradicts the reused one-way state machine: `NEEDS_ATTENTION` is terminal (`job_store.py:85`), `_reclaim_dead_job` (`:672`) parks crashed jobs there, `tick` reclaims at step 0 (`scheduler.py:205`) — no edge back to RUNNING; `WAITING_CAPACITY` absent from `_ALLOWED`. **Fix:** add an explicit `RESUMABLE`/`WAITING_CAPACITY` state with edges `{ADMITTED,RUNNING,TEST,REVIEW}→RESUMABLE→ADMITTED`, have `_reclaim_dead_job` route dead-pgid jobs *with a valid checkpoint* to RESUMABLE (not NEEDS_ATTENTION), and drop the design's "no new states needed" claim. Re-spec the two gate tests against it.
- **F6 [P1, borderline]** OpenRouter `≤$2` sub-ceiling is un-storable: `daily_budget` PK is `day`, no `provider` column (`cost_stops.py:62`); "no migration" (§1) is wrong. **Fix:** either (a) migrate `daily_budget` to composite PK `(day, provider)` with `provider='__nightly__'` default, or (b) spec a *second* named ledger + a defined two-CAS ordering (reserve nightly → reserve OR → on either failure, compensating-release the other) to close the cross-ledger TOCTOU. State the migration.
- **F5 [P1]** Accounting can drift above real provider spend with no bound: Codex is post-hoc metered (`budget_flag:false`), `commit_spend` is overshoot-tolerant (`:314`), and crash-then-resume re-spends a phase while `_reclaim_dead_job` only returns the *reservation*, not the burned tokens. **Fix:** define a numeric tolerance (e.g. ≤ per-job cap × max-failovers), meter+`commit_spend` pre-crash tokens on reclaim, and cap per-job failover count.
- **F8 [P1, test theater]** `test_cost_accounting_reconciles_synthetic_night` reconciles the ledger against itself, not against provider spend — cannot catch F5 drift. **Fix:** feed a synthetic *provider-reported* usage total (distinct from the ledger's) and assert `|provider − ledger| ≤ tolerance`.
- **F3 [P1]** Router pre-filter policy-load path unspecified on a missing `merge-policy.md`: `load_merge_policy` raises `FileNotFoundError` (`merge_policy.py:169`); the design says the router "reads the policy" but not that it catches the raise and substitutes `default_policy` (openrouter-OFF). A naive `except:pass` would leave OR rungs in the ladder. **Fix:** spec "missing/unparseable policy → `default_policy(repo)` (fail-closed)" explicitly in `model_router`. (Guard `:362` still catches, so no leak — but the FIRST wall must not silently no-op.)
- **F2 [P1]** Resume/failover must RECOMPUTE the rung via `select_tier` with the live policy, not replay the checkpoint's persisted `rung` (§3.1 stores `rung:{worker,model,tier}`). A stale cached true-tier on a now-false repo would re-launch on OR (guard still catches → no leak, but first wall bypassed). **Fix:** state that `resume`/`on_429` call `select_tier(repo, …, load-fresh policy)` and ignore the checkpoint's `rung` for admissibility.
- **F1 [P1]** Per-rung pre-filter application is a design assertion with no executable guarantee until code exists; it is the load-bearing behavior of the first wall. **Fix:** make `next_rung` re-filter from `(repo,policy,catalog)` on every call (not from a `select_tier`-cached list) and add a unit test that a false repo's `next_rung` returns `WAIT_FOR_CAPACITY` at every step, never an OR rung.
- **F10 [P1]** "Capture before kill" holds only for supervised kills; the gate's headline *crashed* worker (dead pgid via OOM/`kill -9`) is captured post-mortem by `_reclaim_dead_job` against a dead worktree. **Fix:** split forensic capture into supervised-pre-kill vs. crash-post-mortem paths; scope the gate test to the class it actually exercises.
- **F7 [P2]** Enabling OpenRouter in P4-b (adding `_PROVIDER_MODEL_KEY["openrouter"]`) removes the third *accidental* wall the P3-review P0-1 relied on, making `assert_openrouter_allowed` the sole barrier for OR. **Fix:** note this in §13; it raises the stakes on the guard's correctness and argues for keeping wall-3 (an explicit "no OR key unless policy true" check at key injection) rather than deleting it.
- **F12 [P2]** `GLM-5.2` phantom-model prose is factually wrong: it IS in `capabilities.json` (`zhipuai/GLM-5.2`). **Fix:** correct §2/§4.1/P0-4 wording to "phantom = any name failing `live_catalog && ping_ok`"; pick a genuinely-absent name for the test.
- **F-schema [P2]** `transition(extra=)` f-string-interpolates column names (`job_store.py:320`). Internal-only today; if any P4 caller ever routes an external key into `extra`, it is an injection seam. **Fix:** whitelist the `extra` keys against the known column set.

## Bottom line

The **crown residency risk is closed**: no failover path routes a false-policy job to OpenRouter (two enforced walls + a third accidental one), verified at `worker_runner.py:362` and `residency_guard.py:57-88`. The **$5 hard ceiling is not breachable** (atomic pre-launch CAS at `cost_stops.py:260`). The design does NOT ship as-is because: the crash-resume gate is unimplementable on the reused state machine (F11), the $2 OpenRouter sub-ceiling has nowhere to live (F6, a wrong "no migration" claim), cost accounting can drift above real spend with an undefined tolerance and a self-reconciling test (F5/F8), and two of the six flagship gate tests are theatrical or blocked as written. Fix F11/F6/F5/F8/F3/F2 before BUILD; the rest are cleanups.
