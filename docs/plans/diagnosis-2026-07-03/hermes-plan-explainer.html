Master plan · v3 · factory-first

Drop in a spec at night. Wake to tested pull requests.

Hermes is a program on one Mac that is becoming an autonomous software factory: you hand it coding work, and overnight a fleet of AI workers splits it into tasks, writes and tests the code on isolated copies of the repo, and by morning presents you with finished pull requests you approve from your phone with one tap.

How it works

Six layers, one gate to the outside world

The trust model

Autonomy is earned as data — and revoked instantly

The factory starts by asking for approval on everything. Each repo-plus-task-type combination earns the right to auto-merge only by building a track record. Trust is a ledger, not a vibe: 10 clean merges over 30 days graduates it — a single bad one revokes it.

Track record for one repo × task-type

0 of 10 clean merges. Still tier-0 — every merge is held for your tap.

Tier 0 — start here

Ask for everything

Every merge is held for a human tap. This is the day-one default, and where any repo returns the instant it regresses.

Tier 1 — earned

Auto-merge, personal non-prod only

After ≥10 consecutive clean merges, 0 reverts, over ≥30 days. Graduation is a proposal you approve; demotion is automatic.

Never

Stays human forever

Production deploys, deletions, spending money, and all work/Diligent repos — regardless of track record.

Safety & security

What the agents can never do

These aren't labels — they're enforced by plain code the AI cannot reach. The original failure that started this whole effort was an AI reading a credential off disk and editing its own guard. Every rule below makes that structurally impossible.

✕
Push directly to the outside git push is removed from the worker allowlist entirely. Workers only commit locally; every push and merge goes through the broker.
✕
Spend past the caps Three independent stops: a per-job dollar cap, a wall-clock timeout that kills the process group, and a daily reserved-budget ceiling.
✕
Send confidential code to third-party models A per-repo allow_openrouter flag defaults to false for work/Diligent repos — they wait for subscription capacity rather than spill to third-party hosts.
✕
Touch their own guardrails An immutable-ring denylist rejects, at the merge-submission gate, any diff touching broker source, the trust policy, or cost-stop code — and workers can't even read those paths.

Self-improvement

The factory gets better every week — within a fence

A per-model scorecard rewrites the routing table from real outcomes; a weekly pass improves the skill files; a nightly retro proposes concrete edits. But exactly what the factory may change about itself is drawn as three concentric rings — and the core is off-limits.

Ring 1 · proposal → owner-approved diff

May self-modify

Skill files, prompts, the model-routing table, policy weights, pattern-bank entries. The nightly retro emits a diff; you approve it through the broker; it stays disabled until a skill lint and one behavioral test pass. Never a silent self-edit.

Ring 2 · data-driven, no diff

May auto-tune within bounds

Routing within the ladder, trust-graduation proposals, backpressure thresholds inside a configured min/max. Every auto-tune writes a line to tuning-log.md — timestamp, what changed, from→to, and the data that triggered it — surfaced in the weekly retro.

Ring 3 · never self-modifies

Immutable core

The broker boundary, the trust rules themselves, the three cost stops, the "no AI in the supervisor loop" principle, and the "what never graduates" list. A factory job touching these is rejected at submission — human-initiated and restart-gated only.

Glossary

The words that keep coming up

Every definition lifted from the plan itself. If a term above felt like jargon, it's here.

Broker
A small separate process that is the only thing holding send/push/API credentials. The assistant asks it to act; it checks the rules and either does it or holds it for approval. Because the AI can't read the credentials, it can't bypass the broker.
Worktree
An isolated checkout of a git repo on disk. Each worker gets its own, so parallel workers never overwrite each other's files.
Trust ledger
A table recording, per repo and task-type, how past merges went (clean / needed a fix / rejected / reverted). It's the data that earns or revokes auto-merge.
Verification gauntlet
The chain of checks every change must pass: acceptance tests → the repo's own test suite → an independent second-AI review → an end-to-end demo drive.
Worker
A background AI process (claude -p, codex exec, or an OpenRouter model) that actually writes the code — run without a visible window and controlled by scripts.
Task-splitter
A one-time AI pass per project that turns a spec into an ordered list of small tasks, each with its acceptance tests written first — or parks it and asks you if it's too vague.
Fresh-context verified
A gate checked by a person or AI agent with no prior knowledge of the task, so the builder can never rubber-stamp its own work.
429 / rate limit
HTTP status 429 means "too fast / quota hit." The factory detects it explicitly and steps down to the next cheaper provider — a naive retry can drain a month's quota in minutes.
Headless
Running without a visible window. Workers are headless background processes, launched and killed by scripts.
pm_os
A separate personal-assistant codebase Yu-Kuan already owns (email, calendar, Jira). The plan reuses its plumbing rather than rebuilding those integrations.
Immutable ring
The set of paths — broker source, trust policy, cost-stop code — that plain code refuses to let any diff touch at merge time. The guard being editable is exactly the original failure, made structurally impossible.
Pull request (PR)
A proposed set of code changes submitted for review before merging. The factory produces PRs; you approve or reject them.
